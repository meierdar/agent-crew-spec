# The Sync Problem — And Three Ways To Solve It

## The killer question

Two versions of every story = someone has to keep them in sync.
If you edit the human version and forget to update the agent version
(or vice versa), they diverge. Now you have bugs caused by agents
reading stale instructions.

This is how most dual-format systems die.

## Three approaches

### Approach A: Human writes, machine generates

```
Human writes:  .ai/stories/E001-S003.md       (markdown, full prose)
Script runs:   ai-compile E001-S003.md
Agent reads:   .ai/compiled/E001-S003.agent    (compact DSL, auto-generated)
```

**How it works:** Human writes stories the normal way. A compile
script extracts the structured parts (frontmatter, acceptance criteria,
file references) and generates the agent version. Agent ONLY reads
the compiled version.

**Pros:**
- Human workflow doesn't change
- Single source of truth (the .md file)
- Agent format is always in sync (regenerated on change)
- Can run as a git hook (pre-commit compiles all changed stories)

**Cons:**
- Compile script needs to parse prose to extract structure — fragile
- Loses information that only exists in prose ("the tricky part is...")
- Human has to write prose that the compiler can parse, which constrains
  the prose style

**Verdict:** Sounds clean but the compiler is the weak link. Prose
is inherently unstructured — extracting structured data from it is
the exact problem we're trying to solve.

### Approach B: Agent format is source, human view is generated

```
Human writes:  .ai/stories/E001-S003.md        (structured template)
                → but using the agent-friendly format
Script runs:   ai-render E001-S003.md
Human reads:   BOARD.md, rendered views, dashboards
```

**How it works:** Stories are written in the structured format from
the start. The "human version" isn't a separate file — it's a rendered
view (like BOARD.md is already generated from story frontmatter).

**Pros:**
- Single source of truth
- No sync problem at all
- Agent reads the file directly, no compilation step

**Cons:**
- Humans have to learn the structured format
- Writing `SCOPE +login -password_reset` is less natural than
  writing prose descriptions
- The story file becomes less readable as a standalone document

**Verdict:** This is the cleanest architecture but requires the human
to adapt. That's a real cost — if it's too annoying, people won't use it.

### Approach C: One file, two sections (the hybrid)

```
.ai/stories/E001-S003.md:
  ---
  YAML frontmatter (both human and agent read this)
  ---

  ## Description                    ← HUMAN reads this
  Prose description for context.

  ## A2A                            ← AGENT reads this
  IN .ai/bus/E001.bus @CTX:users-table
  OUT lib/auth/routes.dart NEW
  SCOPE +login -password_reset
  DONE_WHEN tests_pass AND endpoints_match

  ## Acceptance Criteria            ← BOTH read this
  - [ ] Login works
  - [ ] Registration works
```

**How it works:** Same file contains both versions. The agent is
instructed: "Read the ## A2A section for your work spec. If A2A is
absent, fall back to reading the full story." The human writes the
Description for their own understanding. The A2A section is the
precise spec for the agent.

**Pros:**
- Single file, no sync between files
- Human and agent sections coexist
- Graceful degradation (no A2A = agent reads prose, works okay)
- Incremental adoption (add A2A to stories one at a time)
- Git diff shows both versions changing together

**Cons:**
- The Description and A2A could say different things (internal sync)
- Story files get slightly longer
- Someone has to write the A2A section (human or prior agent)

**Verdict:** This is the pragmatic winner. Not the cleanest, but the
most adoptable. And here's the key insight: **the A2A section can be
generated by the ASSIGNING agent or a prep script.** The human writes
the prose, then runs `ai-prep E001-S003.md` which reads the prose and
context bus to generate the A2A section.

---

## My recommendation: Approach C + generation

```
1. Human writes story with prose Description (as today)
2. Human runs: ai-prep .ai/stories/E001-S003.md
   → Script reads the prose + context bus + epic scope
   → Generates the ## A2A section inside the same file
3. Agent reads ## A2A section (structured, dense, unambiguous)
4. If no A2A section exists, agent reads prose (backward compatible)
```

This gives you:
- **No behavior change** for writing stories
- **One file** per story (no sync between files)
- **Graceful degradation** (works without A2A, just less efficiently)
- **The generation step can improve over time** as we learn what
  agents actually need

For the context bus: it's already agent-native (.bus format).
`bus-parse export` generates the human-readable version on demand.
No sync problem because the bus IS the source of truth.

## File layout

```
.ai/
├── stories/
│   └── E001-S003.md          # ONE file: human prose + ## A2A section
├── epics/
│   └── E001.md               # Human-readable (agent reads once, low cost)
├── bus/
│   └── E001.bus              # Agent-native (bus-parse export for humans)
├── signals/
│   └── E001-S003.sig         # Agent-only (ephemeral)
├── roles/
│   └── defaults/             # Human-readable (agent reads once, low cost)
├── dod.md                    # Human-readable (agent reads once)
└── claims/
    └── E001-S003.lock        # Agent-only (coordination)
```

No duplication. No parallel file trees. The bus is the only
agent-native file format, and it has an export command for humans.
Stories are single files with a structured section inside.
