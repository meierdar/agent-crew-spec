# Findings: Does Every File Need Two Layers?

## Short answer: No. Only two file types justify it.

I audited every file an agent reads on startup and measured the waste
(tokens spent on formatting, prose, and disambiguation). The results:

| File | Tokens | Waste | Read freq | Translate? |
|------|--------|-------|-----------|-----------|
| CLAUDE.md | ~250 | ~30 | Once | No — not worth it |
| Role definition | ~150 | ~20 | Once | No — already structured |
| **Story file** | ~200+200 | ~240 | **Every task** | **Yes — biggest win** |
| Epic file | ~200 | ~30 | Once | Partial — scope only |
| **Context/bus** | varies | ~40/entry | **Constantly** | **Yes — already done** |
| DoD | ~200 | ~30 | Once | No — it's a checklist |

The two that matter:

1. **Stories** — ~320 tokens wasted per story (40 on formatting + 200
   on disambiguating prose + 80 on redundant references). Over an
   8-story epic: ~2,560 tokens.

2. **Context bus** — ~40 tokens wasted per entry × 30 entries = ~1,200
   tokens. Already solved in Exp 07.

Everything else is read once per session. Saving 30 tokens on a file
read once is not worth maintaining a second version.

## The sync problem kills parallel files

I evaluated three approaches to keeping human + agent versions in sync:

| Approach | Sync risk | Human effort | Winner? |
|----------|----------|--------------|---------|
| A: Human writes, script compiles | Medium | None | No — compiler is fragile |
| B: Agent format is source | None | Must learn format | No — too much change |
| **C: One file, two sections** | **Low** | **Minimal** | **Yes** |

**Approach C wins because:**
- Single file = no sync between files
- Human and agent sections coexist
- Backward compatible (no A2A section = agent reads prose, works fine)
- The A2A section can be auto-generated by `ai-prep`

## How it actually works

### The workflow

```
1. Human writes story (prose, as today)
   → .ai/stories/E001-S003.md

2. Human (or CI) runs: ai-prep .ai/stories/E001-S003.md
   → Reads prose + context bus + dependencies
   → Injects ## A2A section into the SAME file

3. Agent reads ## A2A section
   → Structured, unambiguous, references bus entries by name
   → Falls back to prose if A2A is absent

4. Agent works, appends to bus
   → .ai/bus/E001.bus gets new @CTX/@DEC/@WARN entries

5. Human wants to see what agents know?
   → bus-parse export .ai/bus/E001.bus
   → Gets human-readable markdown
```

### What the story file looks like

```markdown
---
id: E001-S003
title: "Implement auth API endpoints"
epic: E001
status: ready
assigned_role: backend-developer
critical: true
depends_on:
  - E001-S001
  - E001-S002
---

## A2A

@STORY E001-S003 backend-developer M critical
IN .ai/bus/E001.bus @CTX:users-table
IN .ai/bus/E001.bus @CTX:auth-api-contract
IN .ai/bus/E001.bus @WARN:*
IN .ai/bus/E001.bus @DEC:no-soft-delete
IN .ai/bus/E001.bus @DEC:auth-provider

# E001-S003 — Implement auth API endpoints

## Description
Build the actual API endpoints per the contract, wired to the database.

## Acceptance Criteria
- [ ] Login endpoint works with valid credentials
...
```

The agent reads the A2A block (5 lines, ~80 tokens, zero ambiguity).
The human reads the Description and Acceptance Criteria.
Both look at the frontmatter. Neither is burdened by the other's format.

## The complete system architecture

```
YOU (human)
│
├── Write: stories (.md with prose)
├── Write: epics (.md with goals + scope)
├── Set: priorities, critical flags
├── Run: ai-prep (generates A2A sections)
├── Run: ai-swarm plan (see execution waves)
├── Review: critical stories only
├── Read: bus-parse export (see what agents know)
│
│   ┌─────────── BOUNDARY ───────────┐
│   │                                │
│   ▼                                │
│                                    │
│  AGENT reads:                      │
│  ├── CLAUDE.md (once, as-is)       │  ← human-readable, fine
│  ├── Role file (once, as-is)       │  ← human-readable, fine
│  ├── Story ## A2A (per task)       │  ← AGENT FORMAT
│  ├── .ai/bus/E001.bus (always)     │  ← AGENT FORMAT
│  ├── .ai/signals/ (coordination)   │  ← AGENT FORMAT
│  └── DoD (once, as-is)            │  ← human-readable, fine
│                                    │
│  AGENT writes:                     │
│  ├── Code (the actual work)        │
│  ├── .ai/bus/ (append @CTX/@DEC)   │  ← AGENT FORMAT
│  ├── .ai/signals/ (events)         │  ← AGENT FORMAT
│  └── Story checkboxes + status     │  ← shared format
│                                    │
│   └────────────────────────────────┘
│
├── Read: BOARD.md (auto-generated)
├── Read: bus-parse export (when curious)
└── Read: story files (prose sections)
```

**Three files are agent-format:**
1. Story `## A2A` section (auto-generated, inside the .md)
2. `.ai/bus/*.bus` (agent writes, `bus-parse export` for humans)
3. `.ai/signals/*.sig` (agent-only, ephemeral)

**Everything else stays human-readable.** Roles, CLAUDE.md, DoD,
epics — agents read these once and the formatting waste is negligible.

## What this means for CLAUDE.md

The agent working protocol would add one instruction:

```markdown
## Agent Working Protocol

Before starting any work, follow this sequence:

1. Read your role definition in `.ai/roles/`
2. Read the assigned story — **prioritize the ## A2A section**
   if present; fall back to Description if absent
3. Read the context bus: `.ai/bus/<epic-id>.bus`
4. Read the parent epic for broader context
5. Check `.ai/dod.md` for "done" criteria
6. Work the story, appending to the bus as you make decisions
7. Self-verify against acceptance criteria and DoD
```

Step 2 changes slightly ("prioritize A2A"). Step 3 is new (read bus).
Step 6 is new (write to bus as you work). Everything else is the same.

## The meta-insight

The question was "should agents only read agent-translated files?"

The answer is: **agents should read agent-optimized format for the
files they read REPEATEDLY (stories, context). For files they read
ONCE (role, CLAUDE.md, DoD), the human format is fine.**

The cost of maintaining two formats is only worth it when the savings
compound across many reads. For one-time reads, the 20-30 token
overhead of markdown formatting is cheaper than the complexity of
maintaining a second version.
